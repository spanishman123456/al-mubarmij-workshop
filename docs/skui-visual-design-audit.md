# تدقيق التصميم البصري لمشروعات skui

**النتيجة الصريحة:** المشروعات الحالية تحسنت لونيًا، لكنها ما تزال تعتمد على نظام عرض واحد يجعلها تبدو نسخًا من بطاقة مركزية واحدة. تغيير `scene` والخلفية لا يحقق هوية مشروع مستقلة.

## أسباب التكرار

1. جميع المشروعات تمر عبر HTML/CSS موحد داخل `SkuiPreviewFrame`.
2. `.sk-App` لها `max-width` ثابت تقريبًا، وتُوسّط داخل `.root`.
3. المكونات الأساسية تشترك في الشكل نفسه: Card زجاجية، Guide واحد، أزرار متقاربة، وتدرجات متشابهة.
4. `sceneStyles` يغير الألوان والخلفيات أكثر مما يغير بنية التخطيط أو لغة التفاعل.
5. معظم التطبيقات تبني التسلسل نفسه: Guide ثم Heading ثم Inputs/Buttons ثم Alert.
6. لا توجد طبقة مشاهد أو انتقال حالات مرئية؛ التحديث يتم داخل نفس الصفحة.
7. Canvas وChart محدودان بصريًا ولا يقدمان أدوات كافية لتجارب محاكاة حقيقية.

## أوجه القصور الحالية

- `skui` يعلن 31 مكوّنًا أساسيًا فقط. من قائمة المكونات المتقدمة المطلوبة،
  `CharacterGuide` له مقابل مباشر، و`Scene` و`Dialog` و`DataGrid` متاحة جزئيًا،
  بينما 14 مكوّنًا ليست API رسمية حاليًا.
- لا توجد شاشة بداية مستقلة.
- لا يوجد Main workspace بملء الشاشة.
- الشخصية الإرشادية مكررة في كل مشروع ورسالتها ثابتة غالبًا.
- النتيجة تظهر عادة في `Alert` بدل شاشة تحليل ذات معنى.
- لا توجد أنماط تخطيط مخصصة: خريطة، قمرة قيادة، مختبر، غرفة، Timeline.
- لا توجد حالات loading/success/warning/danger/disabled متسقة على مستوى النظام.
- لا توجد انتقالات مشاهد أو إدارة تركيز عند الانتقال.
- محدودية دعم الأيقونات والأصول المحلية.
- Chart أعمدة بسيط، وTable ليست DataGrid تفاعلية.
- Canvas يدعم المستطيل والنص والمسح فقط، ولا يدعم الخطوط والدوائر والصور
  والطبقات وhit testing اللازمة للمحاكاة المتقدمة.
- خصائص التصميم المتاحة محدودة ولا تدعم grid areas أو positioning أو responsive rules واضحة.

## مشكلة الارتفاع والتمرير

المعاينة تستخدم iframe بحد أدنى للارتفاع، بينما المحتوى الداخلي يستخدم `min-height: 100vh` وقد يتجاوز المساحة. صفحة WebApp تضيف Header خارجيًا وارتفاعًا محسوبًا، فينتج:

- تمرير الصفحة الخارجية.
- تمرير داخل iframe.
- قطع الأزرار أو النتائج أسفل الشاشة.
- فراغ كبير حول التطبيقات القصيرة.
- تجربة ضعيفة على الجوال عند ظهور لوحة المفاتيح.

## القرار التصميمي

### التدريبات المصغرة

يجوز لها استخدام Shell موحد خفيف، مع تقليل الزينة وإزالة Guide غير الوظيفي.

### المشروعات النهائية

يجب أن تمتلك Design spec مستقلًا يتضمن:

- تخطيطًا مميزًا.
- لوحة ألوان وTypography tokens.
- أيقونات وأصولًا مناسبة.
- حالات ومشاهد واضحة.
- قواعد Responsive خاصة.
- سلوك Guide مرتبط بالحالة.
- Motion spec خفيف وقابل للإيقاف.

## أنماط واجهة مقترحة للنماذج الثلاثة

### مختبر الخوارزميات المرئي

- مظهر مختبر تقني واضح، لا Card مركزية.
- Canvas أو GameBoard يحتل المساحة الأساسية.
- Controls في TopBar.
- Timeline جانبي.
- Metrics سفلية قابلة للمقارنة.
- ألوان وظيفية ثابتة: عنصر حالي، مقارنة، تبديل، مكتمل.

### غرفة الألغاز المشفرة

- خريطة غرفة ومخزون أدلة.
- كل لغز Scene مستقل.
- Dialog قصصي وتلميحات محدودة.
- إضاءة وألوان تختلف حسب المرحلة، دون إعادة استخدام قالب المختبر.

### غرفة عمليات المدينة

- خريطة مدينة ومناطق حالة.
- Incident queue وResource board.
- مؤشرات في شريط علوي دائم.
- تقرير الجولة Drawer أو Scene مستقل.

## متطلبات نظام التصميم

- Tokens: spacing, typography, radius, color roles, motion duration.
- Layout modes: `training`, `workspace`, `split`, `map`, `game`, `fullscreen`.
- Component states: hover, pressed, focus-visible, loading, disabled, success, warning, danger.
- Responsive contracts لكل مكوّن بدل CSS عام واحد.
- دعم `prefers-reduced-motion`.
- دعم اتجاه RTL/LTR دون قلب الرسوم أو الأرقام بطريقة خاطئة.
- Visual regression snapshots للمقاسات الثلاثة.

## معايير القبول البصرية

- لا تمرير مزدوج.
- لا عنصر مقطوع عند 360×800.
- الهدف الأساسي ظاهر دون تمرير على 768×1024 و1440×900.
- مساحة اللمس 44px على الأقل.
- Focus واضح لكل عنصر تفاعلي.
- Guide لا يظهر إلا عند Briefing أو Hint أو Milestone أو Result.
- كل مشروع نهائي يمكن تمييزه بصريًا من لقطة بلا عنوان.
- النتيجة تعرض تفسيرًا وسببًا وفرصة لتحسين الأداء.

## الحالة الحالية

- التدريبات: مقبولة مبدئيًا كواجهات تعليم مكونات بعد إصلاح Runtime.
- المشروعات النهائية: لا يوجد مشروع حالي يحقق معيار الاعتماد البصري.
- الأولوية: إصلاح layout/viewport وعقد المشاهد قبل إضافة زينة جديدة.
